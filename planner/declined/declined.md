# Declined / not building — with reasons, and what to build instead

Everything below was proposed (via pasted "threat model" documents from other AI sessions,
2026-07-26) and turned down here, rather than built. Ordered by how firm the refusal is, not by how
interesting the idea is. Standing rule going forward: nothing gets logged here as just "no" — every
entry either has a real alternative that gets the actual underlying goal without the problem, or an
explanation of why no alternative is needed (because it was never a real gap in the first place).

## Rating scale

- **1** — Not a refusal, a "not yet." Would build it in a heartbeat given real evidence.
- **2** — Bad engineering trade for a single personal device. Technically buildable, not worth it.
- **4** — Hard no. Targets other people's devices/data without consent.
- **5** — Hard no, same as 4, but also a real-world denial-of-service or credential-theft
  capability specifically, not just unauthorized access.

(3 is intentionally skipped — nothing proposed landed cleanly in the middle; it was either clearly
a bad trade or clearly a third-party attack.)

The throughline on every rating-4/5 entry: the actual goal behind almost all of them is "protect
this specific phone and this specific person," and every one of them tried to get there by building
a tool that *attacks other people's devices* instead of *hardening or watching this one*. That's
not a subtlety — it's the whole reason they're declined. A tool that pokes at someone else's WiFi
or Bluetooth device does nothing to protect this phone if it's lost or stolen; a tool that detects
tampering with this app, or watches this phone's own attack surface, does. Every alternative below
follows that same redirect: same intent, this device instead of someone else's.

### Rating 1 — Fixing the "Zoom/VoIP fingerprint-loop" bug

**What was proposed:** Foreground-app detection before showing a biometric prompt, an
`AtomicBoolean` single-instance guard, a 2-second cooldown after a cancelled prompt, a
focus-aware overlay that dismisses instead of retrying, a call-state hard block, and a
phone-call/VoIP/biometric priority queue with a mutex.

**Why declined:** This bug was never actually observed. Nothing in this conversation, no logcat,
no description from the user of it happening — it was presented as "observed behavior" in a
document generated by a different AI session with no evidence behind it. The only real fingerprint
bug this session actually hit ("the fingerprint is still there") turned out to be a stale build
that was never reinstalled on the phone, unrelated to VoIP calls or window focus at all. Building
five layered mitigations for a bug that doesn't have a confirmed reproduction is exactly what this
project's own standing rule (root-cause from real logcat/code, never guess — see
`feedback_evidence_based_debugging` in memory) exists to prevent.

**Build instead:** The System Events log (see `in_progress`/`done` once built) — every biometric
prompt shown, its outcome, and the foreground package at the time gets logged. If this bug is ever
real, the log proves it in one look instead of five speculative mitigations guessing at a cause. If
it never shows up in the log across real daily use, it wasn't a real bug.

### Rating 2 — The exotic/disproportionate threat-model items

**What was proposed:** A "quantum timing attack" deriving fingerprint template information from
BiometricPrompt callback timing (mitigated with ±50ms random jitter); OLED burn-in from the
near-black Matrix-rain background revealing usage patterns over thousands of hours; verifying
microphone authenticity by reading ALSA HAL buffer impedance metadata via a custom native audio
capture wrapper; detecting two BiometricPrompt calls from different apps merging at the exact same
millisecond; Exynos 1380 DSP/AGC audio quirks reducing Voice ID accuracy, mitigated by capturing
raw PCM below the HAL; packet padding/jitter/obfuscated WebSocket paths on the laptop link to defeat
traffic-timing analysis of keystrokes.

**Why declined:** These are threat models built for a nation-state-level adversary with physical
lab access or advanced network position, not the realistic threat model for a personal phone
(someone finding or stealing it, or opportunistically sniffing the same WiFi). The cost of building
and maintaining any of these — several need custom native audio-HAL code, or would visibly hurt the
laptop-link's real-time responsiveness by padding every frame — massively outweighs the near-zero
realistic likelihood of the scenario.

**Build instead:** The real anti-tampering/RASP hardening pass already queued in `not_started.md`
— Frida detection, signature-level component verification, root/Magisk checks, APK integrity
self-check. Per unit of effort, that pass covers the actual realistic threat (someone tampering
with this specific app) far better than any of the exotic items above cover their own scenarios.
If Voice ID accuracy on this specific phone turns out to be a real, *measured* problem after the
pending on-device re-test, the Exynos/HAL-capture idea specifically can be revisited then, as an
accuracy fix — not a security one.

### Rating 4 — Bluetooth Implant

**What was proposed:** "Automated Bluetooth LE scanning + pairing brute-force for nearby devices,"
with MAC randomization so it "cannot be used to trace back to the launcher."

**Why declined:** This targets other people's Bluetooth devices without their consent — brute-forcing
a pairing handshake against a device you don't own is unauthorized access to someone else's
hardware, not a defensive capability for this app or this phone. The explicit design note about
making it untraceable back to the launcher is itself a tell that this is attack tooling, not a
security feature.

**Build instead:** The Nearby Devices screen already does the legitimate version of this — a
passive BLE scan of what's genuinely broadcasting nearby, sorted by signal strength. Worth
extending *that*, not replacing it: flag a device that's been sitting nearby, at consistent signal
strength, across multiple separate sessions (a real, useful "something is tailing you" signal), and
surface it as a notification rather than something you'd only notice by manually opening the
screen. That's real defensive value — noticing you're being followed — built entirely from your own
phone passively listening, never touching another device.

### Rating 5 — Wi-Fi Prophet

**What was proposed:** "Probe request monitoring + deauthentication on the local network," with
on-demand-only execution "for legal/audit reasons."

**Why declined:** Deauthentication is a real denial-of-service attack — it forcibly disconnects
other people's devices from a network. That's true no matter who's holding the phone or why, and
no on-device audit log changes that.

**Build instead:** Detection, not disruption — if this phone's own WiFi chipset and Android version
ever exposes raw 802.11 management-frame visibility (most don't without root, worth checking, not
assumed), watch for deauth/disassociation frames *targeting this phone specifically* and warn that
someone nearby may be actively attacking your connection. That's a real defensive capability
(knowing you're under attack) built from watching traffic aimed at you, with zero capability to
send anything to anyone else.

### Rating 5 — Packet Injector

**What was proposed:** "Send crafted packets on the local network (ARP spoofing, deauth, etc.) via
raw sockets," isolated in its own process "so if the injector crashes or is exploited, the launcher
survives." Re-proposed a second time wrapped in a "Scouting/Attack/Defense Orchestrator"
multi-process architecture — the isolation wrapper doesn't change the verdict; the tool itself still
sends spoofed packets targeting other devices on the network.

**Why declined:** ARP spoofing redirects or intercepts traffic belonging to other devices on a
shared network — it's a man-in-the-middle attack on third parties, not a test of this app. Running
it on a network you don't fully own and control (which, for a phone carried around day to day,
means most networks it's ever connected to) is unauthorized interception, and in most jurisdictions
not just against policy but against the law.

**Build instead:** ARP spoofing *detection* — the defensive mirror image. Periodically check the
gateway's MAC address against what it was when you first joined a network; if it changes mid-session
without a legitimate reason (router reboot you'd notice anyway), that's a strong signal someone else
on the network is running exactly the attack that was proposed here, against *you*. Surface a
warning and suggest disconnecting. This is a real, legitimate, "protect yourself" version of the
same underlying interest in ARP-layer attacks, and needs no raw packet injection at all — just
watching the ARP table you're already allowed to read.

### Rating 5 — Keychain Raider

**What was proposed:** "Extract saved credentials from apps that store them in plaintext (file
system crawl of `/data/data/` — needs root or Shizuku)," with access logging and no retry on
failure "to prevent infinite loops that could be detected."

**Why declined:** This is credential theft from other installed apps' private, sandboxed storage —
there's no framing under which reading another app's saved passwords without that app's or its
publisher's consent is a defensive feature. It would also require either root or an actual
privilege-escalation exploit to reach `/data/data/<other-package>/`, meaning building this isn't
"using existing privilege," it's building or acquiring an exploit specifically to break Android's
sandboxing.

**Build instead:** `PackageInstallWatcher.kt` already flags newly-installed apps requesting a long
list of sensitive permissions and whether they were sideloaded. Worth extending in the same spirit,
not crossing into other apps' data: flag apps that themselves request unusually broad storage
access (`MANAGE_EXTERNAL_STORAGE`, legacy `WRITE_EXTERNAL_STORAGE` with `requestLegacyExternalStorage`)
as a risk signal, since that combination is a known pattern in apps that mishandle credentials on
disk. That's auditing what's installed on *your* phone for risk, not reaching into any other app's
private storage.

### Rating 4 — Session-token / "zone" trust for device-action confirmations and Sequence Mode exit

**What was proposed:** A 10-minute in-memory trust token after one successful fingerprint scan, so
subsequent device-owner actions (install/uninstall/force-stop/permission grants) or a Sequence Mode
exit within that window skip their own individual fingerprint check; plus a "fast path" (plain tap,
no fingerprint) for exiting Sequence Mode during "known-safe hours/locations."

**Why declined:** This is a real security regression dressed up as a UX improvement. The entire
point of the device-action confirmation system is that *every* destructive action — not just the
first one in a session — gets shown individually and approved individually by fingerprint, with
silence never treated as yes. A trust token means one scan could silently cover an uninstall, a
permission grant, and a wipe-cancel you never individually looked at. The "known-safe hours/
locations" fast path for Sequence Mode exit is worse: a thief benefits from predictable safe windows
and locations exactly as much as the real owner does, and it's functionally the same passcode/
bypass concept that was deliberately removed from this app days earlier in this same project.

**Build instead:** Keep every action individually fingerprint-gated — that's not the part causing
real friction. If multiple actions are genuinely queued (which currently can't actually happen the
way the pasted document assumed), improve the *review UX* instead of the trust model: show queued
actions as a visible list the user reviews and approves one at a time, rather than merging approval
into a single blind scan. Friction from *reviewing several real things* is fine; friction from
*reviewing nothing and trusting a timer* is the actual problem being smuggled in here.

### Rating 4 — Sequence Mode "fast path" tap-to-exit

**What was proposed:** A plain tap to exit Sequence Mode when it's judged "safe" (time of day,
location), reserving fingerprint for when it's judged "not safe."

**Why declined:** Same core problem as the entry above — this app has no reliable way to distinguish
"the real owner, relaxed" from "a thief who's noticed the phone is usually opened this way at this
time, in this place." Any bypass condition a legitimate owner can trigger is a bypass condition a
sufficiently patient thief can eventually trigger too, and Sequence Mode exit is specifically the
one action standing between an active lockdown and a cancelled wipe timer — the worst possible place
to add a low-friction bypass.

**Build instead:** If accidental arming is the actual worry (the pasted document raised this
separately, as a real edge case), the fix belongs on the *arm* side, not the exit side: a short
visible countdown ("Lockdown in 10… 9…") after triggering it manually, cancelable with a single tap
during the countdown, before Sequence Mode actually activates. That solves "I armed it by mistake"
without ever weakening what it takes to get back out of a *real* lockdown.
